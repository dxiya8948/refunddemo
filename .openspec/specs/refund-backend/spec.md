# 退款后端规范

## 目的

定义按商户隔离的全额退款行为契约，使其可观察、可测试。本文描述当前实现的基线规范，不意味着要对演示数据库发起真实退款操作。

## 需求

### Requirement: 商户身份与数据隔离

所有已定义的 `/api` 接口必须从 Bearer 令牌解析商户身份和角色。订单与退款读取必须限制在当前商户范围内。只读身份不得创建或查证退款。无权访问的资源必须返回 `404`，且不得泄露其他商户数据。

#### Scenario: 跨商户读取

- **GIVEN** 使用商户 A 的 Bearer 令牌，目标订单属于商户 B
- **WHEN** 客户端读取该订单或其退款
- **THEN** API 返回 `404`，且不包含商户 B 的数据

#### Scenario: 只读身份写入

- **GIVEN** 使用只读 Bearer 令牌
- **WHEN** 客户端创建或查证退款
- **THEN** API 返回 `403`，且不调用渠道接口

### Requirement: 全额退款请求校验

创建接口只接受已支付订单、非空且不超过 200 字节的 `Idempotency-Key`，以及仅包含一个 JSON 对象的请求体。`reason` 去除首尾空白后必须非空且不超过 500 字节。API 必须从已存储订单取得金额、币种、商户和原渠道，客户端不能决定这些值。无效请求须返回包含 `code` 和 `message` 的 JSON，且不得提交到渠道。

#### Scenario: 已支付订单可退款

- **GIVEN** 一笔属于当前商户的已支付订单，以及有效的幂等键和原因
- **WHEN** 客户端调用 `POST /api/orders/{orderID}/refunds`
- **THEN** 退款使用该订单的全额、币种和原支付渠道

#### Scenario: 未支付订单被拒绝

- **GIVEN** 一笔未支付订单
- **WHEN** 客户端请求退款
- **THEN** API 返回 `409`，且渠道不产生受理记录

### Requirement: 未知支付状态同步

演示订单 `A-1002` 初始支付状态为 `UNKNOWN`，不得创建退款。当前商户的写身份可通过 `POST /api/orders/{orderID}/sync-payment` 同步状态；仅 `mock-unknown` 渠道上的 `UNKNOWN` 状态可被确认成 `PAID`。该操作必须按商户隔离、只读身份返回 `403`，并且重复调用幂等。正常服务重启及重复初始化不得把已同步的状态改回 `UNKNOWN`；显式重置演示数据后恢复初始未知状态。

#### Scenario: 未知支付先同步再退款

- **GIVEN** A-1002 支付状态为 `UNKNOWN`
- **WHEN** 商户 A 写身份发起退款
- **THEN** API 返回 `409`，且退款渠道没有受理记录
- **WHEN** 商户 A 写身份同步支付状态
- **THEN** 订单状态变为 `PAID`，此后允许正常退款

#### Scenario: 未知支付同步权限和隔离

- **GIVEN** 只读身份或其他商户身份
- **WHEN** 客户端同步 A-1002 的支付状态
- **THEN** 只读身份收到 `403`，其他商户收到 `404`，订单状态不变

### Requirement: 幂等与每单最多一笔退款

每笔订单最多存在一条业务退款。幂等键在单个商户内唯一。同一键、订单、金额和标准化原因的重放必须返回原退款，不得再次提交渠道。复用相同键但改变请求，或为已有退款的订单使用新键，必须返回 `409`。

#### Scenario: 同键重放

- **GIVEN** 某商户、幂等键、订单和原因已有一笔退款
- **WHEN** 完全相同的请求再次到达
- **THEN** 返回原退款，且不产生新的渠道提交

#### Scenario: 不同键并发请求

- **GIVEN** 一笔可退款订单
- **WHEN** 多个有效请求并发使用不同幂等键
- **THEN** 只预占一条持久化退款、最多提交渠道一次；其他请求返回冲突而非服务器错误

### Requirement: 持久化渠道请求身份和不确定结果

调用渠道前，系统必须持久化一条 `PROCESSING` 退款及其渠道名、渠道请求 ID。渠道报错、超时或返回无法识别的状态时，应将结果记为 `UNKNOWN`，不得视为成功，也不得因此创建第二笔退款。

#### Scenario: 渠道受理后响应丢失

- **GIVEN** 渠道已受理原请求，但响应丢失
- **WHEN** 创建退款流程结束
- **THEN** 业务退款保持持久化 `UNKNOWN`，并保留原渠道请求 ID

### Requirement: 模拟结果由初始化订单决定

演示渠道根据已存储订单的渠道模式产生确定性结果。退款申请不得选择或覆盖模拟结果；携带 `X-Demo-Outcome` 的请求返回 `400`，且不得调用渠道。`A-1001` 成功，`A-1002` 首次响应丢失但渠道成功受理，`A-1003` 明确失败。金额按人民币整数分保存，页面按元展示。

#### Scenario: 请求不能覆盖渠道结果

- **GIVEN** 一笔已初始化的演示订单
- **WHEN** 退款申请尝试用 `X-Demo-Outcome` 控制成功或失败
- **THEN** API 拒绝请求，订单和渠道均不新增退款记录

### Requirement: 不重复提交的查证

只有 `PROCESSING` 和 `UNKNOWN` 退款可以查证。查证必须使用已存储渠道和请求 ID 查询，不得再次调用 `SubmitRefund`。查询仍无结论时可以保持 `UNKNOWN`。并发查证不得使终态 `SUCCEEDED` 或 `FAILED` 回退。

#### Scenario: 重启后恢复

- **GIVEN** 一笔 `UNKNOWN` 退款以及持久化的渠道受理结果
- **WHEN** 服务重启后，授权商户发起查证
- **THEN** API 使用原请求 ID 返回渠道结果，且不再次提交

#### Scenario: 终态并发竞争

- **GIVEN** 一次查证已返回终态结果
- **WHEN** 另一并发查询返回 `UNKNOWN`
- **THEN** 数据库中已保存的终态不变

### Requirement: 状态查询与错误响应

API 必须提供按商户隔离的订单列表、订单详情和退款状态读取。退款记录须包含状态、原因、渠道、渠道请求 ID 和时间戳。错误响应须包含 JSON 字段 `code` 和 `message`。`SUCCEEDED`、`FAILED` 为终态；`PROCESSING`、`UNKNOWN` 为非终态。

#### Scenario: 查询退款状态

- **GIVEN** 已认证商户及其退款 ID
- **WHEN** 客户端调用 `GET /api/refunds/{refundID}`
- **THEN** 返回当前持久化状态，且不重新提交退款

## 验证

在 `backend` 目录运行 `go test ./...`。`backend/internal/refunds/http_test.go` 使用临时 SQLite 数据库，覆盖商户隔离、请求校验、幂等、并发、不确定响应、查证和重启恢复。
